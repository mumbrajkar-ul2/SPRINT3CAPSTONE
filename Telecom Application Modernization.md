## What this file is

`docs/domain-specific-spec.md` names four jobs for a telecom operations desk. Staff take a customer order for a circuit. They group a flood of alarms into one incident. They look up how a device is connected and ask for a suggested next step. They check that an approved fix really worked.

The table below has one row per job. Column 2 cites the file that describes the job and says what the running program does with it today. Column 3 names the challenge areas from the 16-step guide that change that job. Column 4 names the playbook file. Column 5 says the concrete change that file asks for.

Challenges 1, 2, 5, 7, 15, and 16, plus the semantic layer and the evidence pack, apply to every row in the same way. They are listed once after the table so the feature rows stay about that feature.

## Worked example

Take the second row and one alarm file fact.

`ALA-00002` has last seen on 23 February 2026 and first seen on 31 July 2026. Last seen is earlier. The API never reads this row today, so a caller cannot see the defect through a route.

S02 records that pair in `docs/02-baseline/data-quality-baseline.md` and marks the `quality_issues.json` hint Confirmed. S03 adds a rule id: alarm `last_seen_at` cannot precede `first_seen_at`. S04-11 has a separate drill from the stale-topology drill. The timestamp drill flags a row shaped like `ALA-00002` and does not open an incident from it. The stale-topology drill checks `stale_topology_flag` only. The duplicate-replay drill checks `dedupe_key`. S07, for a storm, returns the deduped set. A proposed severity cutoff would be marked PROPOSED and would name the owner who must confirm it.
