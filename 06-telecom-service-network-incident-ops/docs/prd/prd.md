## 4. The demo flow

**Pick.** Topology lookup, then an AI recommendation, then a human decision. Alarm-storm dedupe is the deterministic analysis step.

**Reasons.**

1. **Verified Fact.** The recommendation never changes a device. `Project_Intent.md` 5.2 lists "None, if the output stays a recommendation" as the irreversible effect of this flow.
2. **Verified Fact.** Code, policy, tests and audit for this flow already exist. The record route and the summary route (`apps/api/main.py`), the policy tables (`apps/api/services/policy.py`), the guardrail tests (`tests/ai/test_guardrails.py`) and the audit read route (`apps/api/services/audit_query.py` and `apps/api/main.py`) are in the repo. S07 adds the storm route, the recommend route, the approval route and the page.
3. **Verified Fact.** `Project_Intent.md` 6.3 asks for a demo that "completes one flow to a human decision". The approval step is that decision.
4. **Verified Fact.** The two flows that touch a live change need an EXECUTE route. The four gates for EXECUTE are not all present (section 9).
5. **Inference.** The storm step gives the operator a reason to look at a device. It uses `dedupe.py`, which already has tests and no caller.

The failure table names the cause. The reasons list in the response body holds these strings today (`policy.py` lines 231 to 236, `ai_gateway.py` lines 296 to 332). A timeout, an open breaker and a full limit of 10 running calls (N-05): `failmode.schema_failure` and `failmode.timeout`. A model that raises an error: `failmode.schema_failure` only. The id `failmode.model_unreachable` names the cause in this table, in RQ-24 and in RQ-54. The code does not write it. The audit row stores no reasons. This includes the reasons of RQ-30 and RQ-70: they appear in the response body only. A refused call has null `prompt_hash`, `tokens` and `latency_ms` in its audit row. A timeout has them set. A breaker refusal and a full limit look the same in the audit row. S07 keeps this behaviour. **Verified Fact.**


**Forbidden fields.** These never enter a prompt (`policy.prompt_fields`, `rule.forbidden_fields_never_enter_prompt`): `field.device.mgmt_ip`, `field.device.credential_profile`, `field.incident.customer_id`, `field.circuit.customer_id`, `field.service_order.customer_id`. The six credential names never enter a prompt, a log line or an answer: `SHARED_DB_PASSWORD`, `SHARED_DB_USER`, `DATABASE_URL`, `AI_GATEWAY_KEY`, `LEGACY_BATCH_PASSWORD`, `OT_VENDOR_TOKEN`. Only the names are written anywhere. The values are not.

**Limits of the checks (Verified Fact,** `docs/13-security-validation/remediation-backlog.md`**).**

- The command-phrase list is short (D-08). A phrase that means the same as "reboot" but uses other words passes. A harmless sentence that holds the word "apply" is held.
- The checks look at the prompt for forbidden values. They do not look at the model answer for forbidden values (SB-04). The stub sends back a fixed sentence, so the gap has no effect today.
- A secret typed inside an allowed field such as `hostname` is not found (SB-14, D-09).
- The model name and the model version are the same text, `local-sim-v1` (SB-15).
- The reasons list cannot tell an open breaker from a full limit of 10 running calls (N-05). A later ADR may add a flag for it. This PRD adds none.

### How S07 reports a gap

A gap is any choice that this PRD, the YAML and the ADRs do not fix. Examples: a key name, a status code, a field in a reply, a word on the page. S07 does not fill a gap. S07 stops work on that requirement and builds no guess for it. S07 writes the gap in a section called 'PRD gaps' in `docs/demo/evidence.md`. The section is a table with five columns: requirement id, what the PRD lacks, the sources that disagree (file and line), what S07 did, and the owner answer. The owner answer is empty until the owner fills it. If S07 finds no gap, the section holds one line: 'None. S07 found no gap.' S07 reports the stage as PASS only when the section holds that line or every row has an owner answer. S07 repeats each gap row under item 6, Blocking issues, of its final response.

If the owner answers a gap by changing this PRD, the PRD version goes up by one minor step and `traceability.md` gets the same version. S07 then re-checks every requirement row whose text changed, and says so in `docs/demo/evidence.md`. S08 starts only after the PRD version stops changing.
